# Усиленный coding workflow AI40 CodeMind

## Цель

AI40 CodeMind не объявляется «лучшим в мире» без воспроизводимого бенчмарка. Вместо маркетингового обещания workflow усиливает качество там, где это можно проверить: каждая роль получает чёткую область, отдельная критика получает уже собранные выводы, а итог всегда показывает evidence, пробелы и следующий безопасный шаг.

| Этап | Вход | Действие | Выход |
|---|---|---|---|
| 1. Classify | Цель и выбранный режим | Определяет доминирующие инженерные риски | Приоритет ролей и quality criteria |
| 2. Specialists | Один и тот же ограниченный контекст | Параллельные независимые заметки | Findings с рисками, рекомендациями и недостающими данными |
| 3. Critic | Сводка заметок специалистов | Ищет противоречия, непроверенные заявления и слабые места | Список развилок и критичных пробелов |
| 4. Synthesis | Результаты и критика | Формирует приоритеты, evidence и план | Единый engineering brief |
| 5. Quality gate | Число успешных ролей, контекст и critical findings | Устанавливает честный статус готовности | `ready_to_plan`, `needs_context` или `degraded` |

## Task-aware фокус

Все десять ролей сохраняются в панели, чтобы не потерять независимую проверку. Однако итоговая система выделяет фокус в зависимости от типа задачи.

| Режим | Главный фокус | Контроль готовности |
|---|---|---|
| Code review | дефекты, типы, обратная совместимость, безопасность | доказательства с путями/фрагментами и regression tests |
| Bug hunt | воспроизводимость, наблюдения, причинные гипотезы | шаги воспроизведения и различение фактов/гипотез |
| Architecture | границы, API-контракты, компромиссы | альтернативы, migration path и критичные зависимости |
| Test plan | coverage, edge cases, failure modes | тесты до/после изменения и измеримый pass criterion |
| APK plan | Gradle/EAS, signing, Android compatibility | подтверждение конфигурации и release checklist до worker-запуска |

## Evidence-first контракт

Итог не имеет права заявлять, что файлы изменены, тесты пройдены или APK собран, если сервер не получил фактический результат из отдельного одобренного worker. До появления worker итог содержит только анализ, ограничения и approval-plan. Quality gate ограничивает доверие к частично недоступной панели и не скрывает ошибки отдельных ролей.
