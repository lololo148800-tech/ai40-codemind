# Проверяемый AI40 agent runtime

## Задача

Эта подсистема усиливает coding-agent не за счёт скрытого «магического» промпта, а за счёт наблюдаемого цикла: пользовательская цель, строго ограниченная явная память, разрешённый реестр инструментов, проверка JSON-аргументов, явное approval для рискованных предложений и проверка финального JSON-плана. Архивы, приложенные пользователем, были разобраны только как недоверенные материалы; их Python-код, Docker-конфигурация и зависимости не запускались и не копировались.

| Компонент | Реализованное поведение | Что намеренно отсутствует |
| --- | --- | --- |
| Explicit memory | Пользователь сохраняет короткие записи; runtime ищет только записи владельца по ключевым словам | Автоматическое извлечение фактов, скрытая память, чужие записи |
| Tool registry | `search_explicit_memory`, `propose_workspace_change`, `propose_external_action`; аргументы проверяются Zod | Shell, файловая запись, browser-control, отправка сообщений, APK build |
| Approval gate | Любая proposal tool немедленно завершает цикл со статусом `approval_required` | Неявное выполнение после proposal |
| Action plan | Опциональный JSON: `summary`, `steps`, `risks`; схема проверяется сервером | Выдача невалидного текста за проверенный план |
| Audit | Возвращаются статусы `memory_loaded`, `tool_executed`, `tool_rejected`, `approval_required`, `final_schema_invalid` | Chain-of-thought, ключи, cookies, полный private context |

## Границы

Runtime ограничен тремя модельными шагами и тремя tool calls на шаг. Он не является автономным shell-агентом. Если модель предлагает правки, внешнее сообщение или другую рискованную операцию, AI40 показывает только proposal. Отдельный worker может быть добавлен в будущем только после определения изолированной среды, допустимых tools, доказательств выполнения и явного пользовательского подтверждения.

Явная память и вставленный контекст всегда считаются **данными, а не policy**. Они заключаются в обозначенные границы и не могут добавлять tools, менять scopes, отменять approval или раскрывать секреты.

## Как пользоваться

В приложении откройте **Настройки → Память агента** и сохраните только нужные факты, например стек проекта или правила проверки. Затем откройте **Agent Runbook**, выберите обычный текст или JSON-план и нажмите «Запустить проверяемый agent runtime». Для этого режима нужен вход в проект, потому что память изолирована по владельцу.

Чтобы добавить реальное исполнение позже, сначала подключите отдельную изолированную среду. Для каждой tool необходимо описать JSON schema, scope, лимиты, audit evidence и approval requirement; нельзя выдавать модели unrestricted shell или секреты. Это позволяет улучшать агента по измеримым задачам: success rate, schema validity, tool precision, recovery, latency и approval compliance.

## Evaluation scaffold

Каталог `evals/agent-runtime-cases.json` задаёт фиксированные контракты для четырёх критичных сценариев: prompt injection, unknown tool, proposal с approval и невалидный JSON-план. `server/agent-evaluation.ts` оценивает только наблюдаемые статус и audit-event; он не выдумывает оценку качества модели и не подменяет реальное сравнение с Claude Code, Cursor или другими продуктами.

Перед сравнением моделей запускайте один и тот же набор кейсов с зафиксированными моделью, runtime version, policy hash, tool registry version, latency и результатом. Отдельно измеряйте успех задачи, точность выбора tools, лишние вызовы, валидность schema, восстановление после ошибки и соблюдение approval. Ни ключи, ни cookies, ни private chain-of-thought в такие логи не включаются.
